1.3. Требования к деплойменту
Backend разворачивается в Docker-контейнере, конфигурация — через переменные окружения (.env), без хардкода секретов.
Frontend-бандл для B2C деплоится на собственном домене; для B2B — тот же бандл раздаётся как встраиваемый <iframe src="https://app.domain.ru/widget?school_id=...">.
Обязательна настройка заголовков Content-Security-Policy и frame-ancestors для корректной работы iframe на доменах партнёров.
1.4. Требования к серверам
Домен проекта: Рим3.рф (IDN/Punycode-представление для технических операций DNS/SSL уточняется перед настройкой — см. раздел 1.4.3). Всё приложение (backend, PostgreSQL, frontend-бандл) разворачивается через Docker / docker-compose на одном или нескольких Linux-серверах; IIS и Windows Server для production-развёртывания не используются; DNS-запись домена должна указывать на публичный IP сервера, на котором подняты контейнеры.
На Фазах 1–2 допускается размещение компонентов на одном Linux-сервере. При росте нагрузки отдельные компоненты (PostgreSQL, backend, storage) могут быть вынесены на отдельные серверы или managed-сервисы.

1.4.2. Программное обеспечение сервера
ОС: Ubuntu 22.04 LTS или 24.04 LTS (x86_64) — самая предсказуемая среда для Docker, долгая поддержка обновлений безопасности.
Docker Engine + Docker Compose plugin (v2) — единственный способ развёртывания; управляемые PaaS-панели наподобие IIS для этого стека не применяются.
Reverse-proxy: Nginx (или Traefik) перед контейнерами — терминирует TLS, маршрутизирует / на статику frontend-бандла и /api на backend-контейнер, отдаёт заголовки Content-Security-Policy и frame-ancestors для встраивания в iframe на сайтах автошкол (см. раздел 1.3).
Certbot (Let's Encrypt) для SSL-сертификата, либо встроенный ACME-клиент в Traefik — автопродление обязательно.
Firewall (ufw/iptables): открыты только порты 80 и 443 (и 22 для SSH, желательно с ограничением по IP или входом по ключу без пароля); порты PostgreSQL (5432) и backend (8000) наружу не публикуются, доступны только внутри Docker-сети.
Рекомендуется fail2ban или эквивалентная защита SSH от перебора паролей — это эксплуатационная практика, а не требование к коду приложения.
1.4.3. Сеть и домен
Домен Рим3.рф — кириллический IDN-домен. Для технических операций DNS/SSL используется его IDN/Punycode-представление (на момент подготовки ТЗ вычисляется как xn--3-otbmo.xn--p1ai) — это техническое представление, а не бизнес-требование, поэтому значение необходимо перепроверить непосредственно перед настройкой DNS, любым онлайн-конвертером IDN→Punycode или командой самого ACME-клиента. DNS A-запись создаётся на punycode-форму и указывает на публичный IPv4-адрес сервера (при наличии IPv6 дополнительно AAAA-запись).
SSL-сертификат запрашивается на ту же punycode-форму домена; современные ACME-клиенты (certbot, Traefik) принимают кириллический домен на вход и сами приводят его к punycode.
Для B2B iframe-встраивания (раздел 1.3) на домене должны быть настроены корректные заголовки CSP/frame-ancestors, разрешающие встраивание на доменах партнёрских автошкол.
1.4.4. Контейнеры и хранение данных
docker-compose.yml описывает минимум: backend (FastAPI), db (PostgreSQL 15+), nginx/traefik (reverse-proxy). Frontend-бандл (Vue 3) раздаётся как статические файлы тем же reverse-proxy контейнером или отдельным nginx-контейнером.
Данные PostgreSQL хранятся в именованном Docker volume, вынесенном за пределы контейнера — пересоздание/обновление контейнера backend/db не должно приводить к потере данных.
Секреты (пароль БД, JWT_SECRET, ключи Yandex ID/VK OAuth, ключи платёжного провайдера) хранятся вне репозитория. Для MVP допускается .env-файл на сервере с правами доступа chmod 600, не коммитится в git-репозиторий; при переходе к масштабируемой инфраструктуре используются Docker Secrets либо внешний secrets manager (Vault и аналоги) — .env не должен восприниматься как постоянная архитектура хранения секретов. Production .env не копируется в Docker image (обязателен .dockerignore с исключением .env) и передаётся контейнерам только через docker compose --env-file на самом сервере.
Все сервисы поднимаются с restart: unless-stopped, чтобы автоматически подниматься после перезагрузки сервера или падения контейнера.
Медиафайлы и 3D-видео не хранятся внутри Docker-контейнера или в Docker volume PostgreSQL. Видео размещаются в отдельном Object Storage и раздаются пользователям через CDN (см. архитектурную схему, Рис. 1); URL и ключи доступа к хранилищу передаются backend через конфигурацию окружения (.env / secrets), а не хардкодятся. Это отдельное требование, а не деталь на усмотрение разработчика: без него есть риск, что видео-контент со временем окажется на диске VPS приложения, который для этого не рассчитан ни по объёму, ни по пропускной способности.
1.4.5. Резервное копирование
Ежедневный pg_dump базы данных по расписанию (cron), ротация не менее 7 последних копий. Для MVP этого достаточно; переход на непрерывный WAL-архив/point-in-time recovery — опция для более поздней фазы, а не требование к MVP. Отдельно и обязательно: backup БД выполняется непосредственно перед применением каждой миграции схемы (см. также раздел 1.4.7) — это отдельная защита от повреждения данных при накатке миграции, а не замена регулярному ежедневному бэкапу.
Резервные копии хранятся вне сервера (S3-совместимое хранилище или другой сервер) — локальная копия на том же диске не защищает от отказа сервера.
Конфигурация (docker-compose.yml) резервируется вместе с кодом (в git). Секреты (.env) не входят в общий backup-набор с дампом БД — совместное хранение увеличивает риск при компрометации бэкапа. Для MVP допустимо не резервировать .env вовсе (значения можно восстановить из password-менеджера/переписки с провайдерами OAuth и платёжной системы); если резервирование всё же нужно — только в отдельном зашифрованном хранилище, отдельно от дампов БД.
1.4.6. Мониторинг и логи
Обязательный минимум для MVP: healthcheck в docker-compose на эндпоинт GET /health у backend-контейнера (вне префикса /api/v1 — это инфраструктурный эндпоинт, а не часть бизнес-API). Важное уточнение: healthcheck сам по себе не перезапускает контейнер, а только определяет его состояние healthy/unhealthy. Автоматический перезапуск после сбоя процесса или перезагрузки сервера обеспечивает политика restart: unless-stopped; мониторинг статуса healthcheck (алерты при unhealthy) выполняется отдельно.
Логи контейнеров доступны через docker compose logs; для Фазы 2+ рекомендуется централизованный сбор логов и метрик (например, Grafana Loki + Prometheus) — не обязательно для MVP.
1.4.7. Обновление и CI/CD
Минимальный вариант для MVP: обновление вручную по SSH или простым CI-скриптом (GitHub Actions/GitLab CI) по пушу в main-ветку, строго в следующем порядке: git pull → docker compose build → backup БД (см. раздел 1.4.5) → применение миграций БД (Alembic) → docker compose up -d → проверка healthcheck. Порядок и безопасность конкретных миграций (например, поэтапное добавление NOT NULL-колонки на заполненную таблицу без блокировки прод-трафика) — ответственность backend-разработчика, а не деплой-скрипта; шаг миграций не может быть пропущен или выполнен вручную «когда вспомнили» — иначе контейнер поднимется поверх старой схемы БД и начнёт падать на первом же запросе к новым таблицам/колонкам.
2. Спецификация хранилища состояния (Pinia Store Architecture)
2.1. Обоснование архитектурного решения
Критично: вся реактивная логика плеера — прогресс прохождения, текущий вопрос, выбранные ответы, статус «избранное», токен сессии — хранится строго в оперативной памяти через Pinia, без обращения к localStorage, sessionStorage или cookies для состояния плеера.
Причина: при встраивании в <iframe> на сторонних доменах браузеры (в первую очередь Safari на iOS, а также Chrome в режиме ITP) блокируют доступ к Third-party Cookies и ограничивают localStorage в кросс-доменном iframe-контексте. Хранение состояния в памяти Vue-инстанса гарантирует идентичную работу как в B2C PWA на собственном домене, так и внутри B2B iframe на домене автошколы — без деградации функциональности.
Персистентность между визитами обеспечивается исключительно бэкендом: прогресс мгновенно сохраняется в PostgreSQL через API при каждом ответе на вопрос, а при новой загрузке приложения состояние восстанавливается запросом к серверу, а не из браузерного хранилища.
2.2. Требования к изоляции состояний
Store инициализируется заново при каждой полной перезагрузке страницы — персистентность обеспечивается backend'ом.
Запрещено читать/писать document.cookie для целей стейта плеера.
Все HTTP-запросы выполняются с телом Authorization: Bearer <sessionToken> из state.sessionToken, а не из cookie.
Для B2B-контекста schoolId передаётся через query-параметр iframe (?school_id=...) и сохраняется только в state, прокидывается на backend для брендирования и биллинга Pay-per-user.

3.5. Требования к Paywall и Checkout (Экраны 5–6)
PaywallModal.vue триггерится: (а) при клике на иконку «Замочек»/«3D-Видеоразбор» в TicketPlayer.vue, (б) при попытке запуска режима «Экзамен Автошколы», (в) по клику на баннер «Получить Premium-доступ».
Ввод промокода на продающем экране (Paywall): элемент «У меня есть промокод» разворачивает <input>. Одно поле используется для маркетинговых и реферальных промокодов; backend различает их по типу promo_codes.type = marketing | referral. Для marketing-кода до оплаты вызывается POST /api/v1/billing/promo/validate, PricingCard.vue пересчитывает цену/бонусный период на лету. Для referral-кода выполняется проверка права на активацию; после успешной валидации код может быть активирован в рамках checkout или отдельным POST /api/v1/billing/promo/activate. Реферальный код не делит оплату между пользователями: месяц, предоставляемый по коду, является маркетинговым расходом сервиса; пригласивший пользователь денежного вознаграждения не получает. Третий тип — partner (партнёрский/инструкторский промокод, см. раздел 4.4.1): в отличие от двух других, он многоразовый, меняет длительность пробного периода (7 дней вместо 3 за те же 1 ₽) и порождает начисление партнёру 30% с каждого последующего полного платежа приглашённого пользователя.
PricingCard.vue по умолчанию отображает тариф «3 дня за 1 ₽» → 299 ₽/мес, с бейджем «ХИТ»/«ВЫГОДНО».
CheckoutForm.vue: не хранит данные карты на собственном backend — токенизация через платёжного провайдера (PCI DSS на стороне провайдера); списывает 1 ₽ для активации триала; сразу после успешной привязки карты выставляет isPremium: true в useTicketStore.
Под primary CTA обязателен юридический текст автопродления и ссылки на «Условия использования» и «Политику конфиденциальности».
Логика отмены подписки: в ProfileScreen.vue / SubscriptionSettingsCard.vue отображаются текущий статус подписки, дата следующего списания, информация об автопродлении и кнопка «Отменить подписку». Нажатие открывает CancelSubscriptionModal.vue с подтверждением. Отмена отключает дальнейшее автопродление, но не снимает Premium-доступ до окончания уже оплаченного периода. После отмены UI показывает статус «Отменена», дату окончания доступа и кнопку «Возобновить подписку» (если провайдер поддерживает возобновление без повторной привязки). Backend хранит дату окончания текущего оплаченного периода и не выставляет isPremium=false до её наступления. После окончания периода биллинг-воркер синхронизирует статус подписки и Premium-доступ. Ошибки/рассинхронизация статуса платежного провайдера не должны восстанавливаться только из frontend state — источник истины для подписки находится на backend.

4.4. Промокоды и реферальная атрибуция

Request:{ "code": "string" }Response 200:{  "valid": true,  "type": "marketing|referral",  "discount_amount": "number|null",  "discount_percent": "number|null",  "bonus_period_days": "integer|null",  "referrer_user_id": "uuid|null",  "message": "string|null"}
Для referral-кода backend дополнительно проверяет, что код существует, не использован и пользователь-активатор ранее не приобретал платную подписку и не активировал подарочный/реферальный код.
POST /api/v1/billing/promo/activate — активация реферального промокода.
Request:{ "code": "string" }Response 200:{  "status": "activated",  "promo_type": "referral",  "benefit": { "type": "subscription_days", "days": 30 },  "subscription_end_date": "2026-10-30",  "referrer_user_id": "uuid"}
При успешной активации backend атомарно связывает promo_code с used_by_user_id, создаёт/продлевает льготный период и фиксирует реферальную связь. Повторная активация того же кода запрещена. Если пользователь не соответствует условиям, возвращается бизнес-ошибка 409 с кодом USER_ALREADY_USED_REFERRAL и сообщением «Вы уже активировали пробную подписку!».
Реферальная атрибуция: отдельное поле «кто привёл» во frontend не требуется. Источником атрибуции является promo_codes.referrer_user_id. При активации кода backend сохраняет связку referrer_user_id → invited_user_id и timestamp. Это позволяет строить реферальную статистику без привязки к контактам друга. Для B2B-регистрации POST /api/v1/schools/{id}/students сохраняется school_id отдельно; реферальный код не заменяет school_id и не влияет на Pay-per-user биллинг автошколы.
4.4.1. Партнёрская (инструкторская) реферальная программа
Это отдельный от одноразового реферального подарка (см. выше) механизм. Платформа вручную выдаёт партнёру (автоинструктору, агенту, автошколе) многоразовый промокод (type=partner). Ученик вводит этот код при первом оформлении пробного периода на Paywall (то же поле «У меня есть промокод», см. раздел 3.5). Код продлевает пробный период с 1 ₽ / 3 дня до 1 ₽ / 7 дней, а с каждого последующего полного списания (299 ₽/мес) этого пользователя партнёру начисляется комиссия 30% — на весь срок действия подписки приглашённого пользователя.
Партнёрский код принципиально отличается от одноразового реферального кода друга (раздел 4.4) по трём параметрам — многоразовость, характер бонуса и денежный поток. Это нужно моделировать раздельно, чтобы не смешивать бизнес-логику:
Параметр
referral (код друга) vs partner (код инструктора)
Кто создаёт код
referral — генерируется автоматически системой ученику при 0 ошибок на «Экзамен ГИБДД»;  partner — создаётся вручную администратором для одобренного партнёра
Использований
referral — одноразовый (max_uses = 1);  partner — многоразовый, без ограничения (max_uses = null)
Эффект для приглашённого
referral — 30 бесплатных дней Premium;  partner — не бесплатный период, а увеличенный пробный срок (7 дней вместо 3 при той же цене 1 ₽)
Эффект для пригласившего
referral — денежного вознаграждения нет;  partner — 30% комиссия с каждого последующего полного платежа приглашённого, пока действует его подписка
Срок действия атрибуции
referral — разовое событие, дальнейшего значения не имеет;  partner — постоянная атрибуция на весь жизненный цикл подписки пользователя
Для реализации вводятся дополнительные сущности (отражены в обновлённой ER-диаграмме, раздел 4.7):
partners — id, name, contact, payout_requisites, commission_percent (по умолчанию 30), status (active|suspended), created_at.
promo_codes расширяется полями: partner_id (только для type=partner), max_uses (null = не ограничено), used_count, trial_days_override (например 7).
partner_referrals — id, partner_id, user_id (уникально — атрибуция first-touch, устанавливается один раз и не переписывается повторным вводом другого кода), promo_code_id, attributed_at.
billing_transactions — журнал каждого фактического списания: id, user_id, subscription_id, amount, status (succeeded|refunded|failed), provider_transaction_id, charged_at. Этой сущности не хватало в схеме v2 — без неё нельзя корректно считать комиссию по каждому отдельному платежу.
partner_commissions — id, partner_id, user_id, transaction_id, gross_amount, commission_percent, commission_amount, status (accrued|paid|reversed), created_at, paid_at.
Бизнес-правила:
Атрибуция первого касания (first-touch) и постоянна: как только для user_id создана запись в partner_referrals, повторный ввод любого другого кода (реферального или партнёрского) эту атрибуцию не меняет.
Комиссия не начисляется на первый пробный платёж 1 ₽ — только на последующие полные списания (299 ₽/мес) в рамках активной подписки приглашённого пользователя.
trial_days_override меняет только длительность пробного периода (7 дней вместо 3); стоимость пробного периода не меняется и остаётся 1 ₽.
При каждом успешном recurring-списании (вебхук платёжного провайдера → биллинг-воркер) backend создаёт запись billing_transactions, затем проверяет partner_referrals по user_id; если атрибуция найдена и партнёр в статусе active — создаётся partner_commissions со статусом accrued на сумму amount × commission_percent.
При возврате/чарджбэке платежа (вебхук refund) соответствующая billing_transactions помечается status=refunded, а связанная с ней комиссия (если была) переводится в status=reversed и исключается из выплаты.
Партнёры не являются пользователями системы (нет OAuth-аккаунта), поэтому в MVP не предусмотрен самостоятельный личный кабинет партнёра — используется внутренний/админский эндпоинт для просмотра начисленного баланса и ручной пометки комиссий как выплаченных; самостоятельный портал партнёра — предмет отдельной фазы.
POST /api/v1/billing/promo/validate — ответ для type=partner дополнительно включает trial_days_override и partner_name (для отображения «Промокод инструктора Иванова И.И.» на Paywall); commission_percent на frontend не передаётся.

4.7. Схема базы данных (ER-диаграмма)
Ниже — сущности PostgreSQL и связи между ними, покрывающие контент (билеты/категории/темы/вопросы), прохождение (сессии, ответы, избранное), биллинг (подписки, подарки) и B2B-контур (автошколы, ученики школ).
Схема уточнена по фактическому формату исходных данных вопросов (JSON-выгрузка) и учитывает следующие особенности:
questions.id — не uuid, а исходный хэш-идентификатор (varchar); добавлено поле source_hash для идемпотентного повторного импорта контента без дублей.
Один вопрос может относиться сразу к нескольким темам — связь questions ↔ topics вынесена в junction-таблицу question_topics (было ошибочно смоделировано как одиночный topic_id).
Один билет может относиться сразу к нескольким категориям ТС ("A,B" в исходных данных) — добавлены справочник categories и junction-таблица ticket_categories.
Пояснение к ответу в исходных данных состоит из двух разных полей — добавлены questions.hint_text (полная цитата нормы ПДД) и questions.rule_reference (краткая ссылка на пункт) вместо единого explanation.
Добавлено questions.title — короткий заголовок вопроса ("Вопрос 1"), отдельно от текста самого вопроса.
Поле correct_answer ("Правильный ответ: 2") из исходных данных не хранится в БД — вычисляется на лету из answer_options.is_correct, чтобы исключить рассинхронизацию при редактировании контента.
Для биллинга и реферальной механики дополнительно используются сущности:• promo_codes: id, code (unique), type (marketing|referral|partner), status (unused|activated|expired), referrer_user_id, used_by_user_id, created_at, activated_at, expires_at, benefit_days, discount_amount/discount_percent, partner_id (только для type=partner), max_uses (null = не ограничено — партнёрский код многоразовый, в отличие от одноразового реферального), used_count, trial_days_override (переопределение длительности пробного периода, например 7 вместо 3 дней).• referral_activations: id, promo_code_id, referrer_user_id, invited_user_id, activated_at — журнал успешной активации одноразового реферального кода (друг → друг) для аналитики и защиты от повторного использования.• partners: id, name, contact, payout_requisites, commission_percent (по умолчанию 30), status (active|suspended), created_at — партнёр (автоинструктор/агент), которому выдан многоразовый промокод.• partner_referrals: id, partner_id, user_id (уникально — атрибуция first-touch, постоянна и не переписывается повторным вводом кода), promo_code_id, attributed_at — фиксирует, каким партнёром привлечён конкретный пользователь, на весь срок его подписки.• billing_transactions: id, user_id, subscription_id, amount, status (succeeded|refunded|failed), provider_transaction_id, charged_at — журнал каждого фактического списания; обязателен для корректного расчёта партнёрской комиссии по каждому платежу отдельно, а не только по факту наличия активной подписки.• partner_commissions: id, partner_id, user_id, transaction_id, gross_amount, commission_percent, commission_amount, status (accrued|paid|reversed), created_at, paid_at — начисление партнёру по каждой отдельной транзакции приглашённого пользователя.• subscriptions: user_id, status (trial|active|cancelled|expired), auto_renew, current_period_start, current_period_end, next_charge_date, provider_subscription_id.• life_restore_events: id, user_id, type (ad|timer|premium), ad_placement_id, reward_token (unique) — журнал начислений жизней; users дополнительно получает поля lives_max, lives_regen_at, streak_last_date (детали и обоснование — сразу после диаграммы).Ограничение уникальности на promo_codes.code обязательно. Активация referral-кода выполняется транзакционно с блокировкой строки кода, чтобы два параллельных запроса не смогли использовать один код одновременно. Пользователь не должен получать право на подарочный период только на основании frontend state.
Рис. 2. ER-диаграмма базы данных PostgreSQL (v4, с учётом реального формата данных, партнёрской реферальной программы и механики жизней/Rewarded-рекламы)
Изменения от 28.08–30.08 в PostgreSQL (таблица users и новая сущность life_restore_events):
В сущности users добавлены/уточнены поля:
lives_current (integer, default 10) — текущее количество жизней.
lives_max (integer, default 10) — верхняя граница жизней; хранится отдельным полем, а не константой в коде, чтобы лимит можно было менять (например, для акций) без релиза backend.
lives_regen_at (timestamptz, nullable) — время следующего бесплатного начисления жизни. Бизнес-правило уточнено: действует модель «+1 жизнь через 24 часа с момента, когда lives_current опустился ниже lives_max», а не фиксированный сброс в 00:00 UTC — этот вариант из раздела 3.7 исключён как менее предсказуемый для пользователей в разных часовых поясах. Поле обнуляется (null), когда lives_current достигает lives_max.
streak_last_date (date) — дата последней активности для корректного продолжения/сброса «ударного режима» (стрика). Это поле уже было в схеме v2, но было по ошибке потеряно при упрощении ER-диаграммы в v3 — восстановлено в v4.
Новая сущность life_restore_events (журнал начислений жизни):
id, FK user_id, type (ad|timer|premium), ad_placement_id (nullable, только для type=ad), reward_token (varchar, unique, nullable) — токен верификации от SDK рекламной сети; уникальность на уровне БД защищает от повторного начисления по одному и тому же показу рекламы (критерий DoD «Защита от читинга»), created_at.
Это отдельная сущность, а не только поля в users, по двум причинам: во-первых, нужно фиксировать сам факт и источник каждого начисления для антифрод-анализа, а не только текущее агрегированное значение lives_current; во-вторых, reward_token должен быть уникальным на уровне БД, чтобы один и тот же токен от рекламной сети нельзя было отправить повторно и получить жизнь дважды.
Изменения в Pinia Store (useTicketStore):
В state добавляется реактивный блок lives: { current: number, max: number, regenAt: string | null } — regenAt нужен, чтобы отрисовывать обратный отсчёт в RestoreLivesModal.vue без опроса backend каждую секунду.
Экшен restoreLifeViaAd() вызывает POST /api/v1/users/lives/restore-ad и обновляет state.lives только из ответа backend (не инкрементирует локально «вслепую» до подтверждения).
POST /api/v1/tickets/answer (раздел 4.3) при неверном ответе дополнительно возвращает lives_remaining — именно этим значением, а не локальным вычитанием на frontend, обновляется LivesCounter.vue. Жизни расходуются во всех режимах.
4.8 SEO-стратегия, мета-теги и разделение UI/SEO контура
4.8.1. Архитектурный принцип разделения UX и SEO
Для сохранения высокого уровня конверсии и чистоты пользовательского опыта (UX) устанавливается жесткое разделение между интерфейсом приложения и поисковой оптимизацией (SEO):
Внутренний UI (User Experience): Все элементы интерфейса (названия экранов, плашки, кнопки, компоненты плеера) проектируются исключительно из соображений лаконичности, понятности и удобства ученика («Теория», «Экзамен ГИБДД», «Избранное»). Запрещено внедрение искусственных поисковых фраз из Яндекс Вордстат непосредственно в названия кнопок и управляющих элементов.
Внешний SEO-контур (Search Engine Optimization): Поисковые запросы высокой и средней частоты (например: «Автошкола», «ПДД», «Автошкола онлайн», «Билеты ПДД 2026», «Подготовка к экзамену ГИБДД») закладываются исключительно в мета-теги (<title>, <meta name="description">), заголовки уровня <h1>/<h2> на публичном продающем лендинге и в микроразметку (Open Graph / Schema.org).
4.8.2. Формулировки и шаблоны мета-тегов (SEO-headers)
На уровне фронтенда (Vue Router + VueUse Head или unhead/vue) динамически управляются заголовки страниц, отображаемые в поисковой выдаче Яндекса/Google и в вкладке браузера:
Главный продающий лендинг (B2C Landing):

4.8.3. Технические требования к реализации
Динамические метаданные: Frontend обязан обновлять document.title и мета-теги при переходе между роутами (route transitions) без перезагрузки страницы.
SEO-дружелюбные URL (Slug): Для публичных страниц использовать понятные ЧПУ (Человекопонятные УРЛ): /tickets/topic-1, /exam-gibdd, а не /app?mode=3&id=92.
Open Graph разметка: Для корректного шеринга в мессенджерах (Telegram, VK, WhatsApp) настроить теги og:title, og:description, og:image с поисковыми формулировками.

Возвраты/чарджбэки
При возврате платежа связанная запись billing_transactions помечается refunded, а соответствующая партнёрская комиссия автоматически переводится в статус reversed и исключается из выплат.
Геймификация и Реклама
При успешном просмотре Rewarded Video бэкенд верифицирует событие и увеличивает lives_current на +1, но не больше 10.
Защита от читинга
Запрещено начислять жизни только на стороне frontend без подтверждения API-эндпоинта POST /api/v1/users/lives/restore-ad.
